# MVP Spec: 求职助手（职位检索 / 简历优化 / 学习 / 模拟面试）

来源：wayfinder map #1 的 11 个决策 ticket（#2-#12）+ ADR-0001~0007 + CONTEXT.md 术语表 + docs/architecture.md + DESIGN.md。
测试 seam 已确认：**services 层（唯一）**，db 注入。

## Problem Statement

校招求职者（秋招，国企/大厂/私企）的信息与准备链路分散：职位信息散落在各渠道（官网/牛客/猎聘），用表格或记忆跟踪网申窗口；简历用通用文档工具改，无法针对每个岗位的 JD 调整；为岗位要求的技术学习缺乏清单与追踪；模拟面试找不到真人陪练。核心痛点：**无法围绕"岗位匹配度"形成从职位到面试的闭环**——不知道某个岗位自己匹配多少、缺什么、该怎么补。

## Solution

一个本地桌面应用，四个模块闭环：

1. **职位检索**：手动录入 + 试点爬虫（牛客校招日程、猎聘校招）采集校招职位卡（公司/岗位/JD/投递渠道/网申窗口/批次/企业性质），预览确认后入库，去重更新；投递状态全程跟踪
2. **简历**：创建/上传基准简历（可多份；docx/PDF 解析为草稿、人工确认）；选中职位卡后一键按 JD 生成优化简历（严格模式：不虚构），匹配度 5 维度评分 + 依据清单 + 并排对比 + 改动理由，确认后入库
3. **学习**：从 JD 分析 + 简历缺口 + 项目技术栈自动生成学习清单（优先级排序），teach 技能驱动教学会话（聊天式、跨次续接），三态进度追踪
4. **模拟面试**：针对职位卡启动语音模拟面试（按住说话，本地 ASR），面试官按结构化流程（开场/技术面/反问/收尾）动态提问，结束生成结构化复盘（4 维度评分 + 薄弱点 + 参考答案），薄弱点一键回填学习清单

## User Stories

### 通用

1. 作为求职者，我希望应用启动后能进入四个模块（职位/简历/学习/面试）中的任意一个，以便按需使用
2. 作为求职者，我希望所有数据保存在本地 SQLite 单文件库中，以便离线可用、隐私安全
3. 作为求职者，我希望应用的领域术语与「职位卡」「基准简历」「优化简历」「匹配度」「学习条目」等一致，以便与面试复盘、学习清单互相引用时不产生歧义
4. 作为求职者，我希望通过侧边栏在四个模块（职位/简历/学习/面试）间切换，以便快速定位功能
5. 作为求职者，我希望首次启动时引导配置模型提供商与 API key，以便 agent 功能可用
6. 作为求职者，我希望设置页可查看/修改模型配置，以便更换模型或修复认证
7. 作为求职者，我希望未配置模型/断网时：职位/简历/采集等手动功能照常可用，优化/学习/面试等 agent 功能明确提示需配置，以便应用不至于整体不可用
8. 作为求职者，我希望配置模型后可「测试连接」验证可用性，以便确认配置有效

### 职位模块

9. 作为求职者，我希望手动录入职位卡（公司/岗位/企业性质/JD/城市/渠道/网申起止/批次/备注），以便跟踪校招职位
10. 作为求职者，我希望企业性质从枚举中选择（央企/国企/大厂/私企/外企/事业单位/其他），以便按投递策略分类
11. 作为求职者，我希望职位卡包含投递渠道与投递入口链接，以便一键跳转投递
12. 作为求职者，我希望职位列表支持按企业性质/批次/投递状态/秋招季筛选，以便聚焦目标
13. 作为求职者，我希望看到每个职位的网申截止倒计时（无截止时间显示"待核实"），以便不错过投递窗口
14. 作为求职者，我希望编辑职位卡任意字段（JD 更新、截止修正），以便保持信息准确
15. 作为求职者，我希望手动触发从牛客校招日程采集职位，预览确认后批量入库，以便快速建立职位库
16. 作为求职者，我希望采集支持两种模式：按公司名/关键词筛选、全量拉取当季列表，以便按需采集
17. 作为求职者，我希望从猎聘校招采集职位（猎聘无截止时间时 end_date 为空并标"待核实"），以便补充牛客覆盖弱的行业
18. 作为求职者，我希望同一来源 URL 的职位重复采集时更新而非新建（刷新 JD/网申窗口），以便信息不重复不陈旧
19. 作为求职者，我希望手动录入与采集到的同一职位（公司+岗位+秋招季相同）合并更新，以便不产生重复职位卡
20. 作为求职者，我希望采集预览页显示"将新增 N 条 / 更新 M 条"与缺字段标记，以便入库前把关
21. 作为求职者，我希望采集过程有请求间隔节流与失败重试，以便不触发目标站反爬
22. 作为求职者，我希望单次采集有数量上限，超限截断并提示，以便控制风险
23. 作为求职者，我希望每次采集有留痕（来源/模式/新增/更新/失败数），以便追溯数据来源
24. 作为求职者，我希望对职位卡进行投递状态跟踪：收藏未投 → 已投 → 面试中 → offer/已拒绝（可放弃），以便管理求职进度
25. 作为求职者，我希望每条投递记录含投递时间与实际渠道，以便复盘投递节奏
26. 作为求职者，我希望查看职位卡完整 JD 全文，以便作为简历优化与面试准备的依据
27. 作为求职者，我希望删除不再关注的职位卡，以便清理列表

### 简历模块

28. 作为求职者，我希望创建多份基准简历（如技术向/国企向各一份），各自独立编辑，以便覆盖不同投递方向
29. 作为求职者，我希望上传 docx/PDF 简历自动解析为结构化草稿，人工确认后成为基准简历，以便复用已有简历
30. 作为求职者，我希望基准简历覆盖教育（GPA/排名/相关课程/荣誉）、技能（分类/熟练度）、项目（要点/技术栈）、实习、证书、自我评价、作品链接，以便覆盖校招投递要求
31. 作为求职者，我希望基准简历可填国企向字段（政治面貌/生源地/生日/性别），以便投递国企央企
32. 作为求职者，我希望简历以 A4 样式预览并导出 PDF，以便直接投递
33. 作为求职者，我希望选择某职位卡后一键生成针对该 JD 的优化简历，以便提高岗位匹配度
34. 作为求职者，我希望优化过程默认严格模式：不虚构项目/经历/数字，仅措辞强化、突出相关、重组顺序、删减无关，以便简历经得起面试验证
35. 作为求职者，我希望看到匹配度评分：总分 + 5 维度分（关键词覆盖/技能/项目相关/经历相关/学历专业）与命中/缺失依据清单，以便知道差在哪
36. 作为求职者，我希望 LLM 不可用时规则层匹配度评分仍可用（仅缺 LLM 定性分析），以便离线也能评估匹配
37. 作为求职者，我希望看到优化稿与基准简历的并排对比，每条改动附理由，以便判断是否接受
38. 作为求职者，我希望优化稿可编辑，确认后才保存为派生稿（关联职位卡），以便防幻觉内容入库
39. 作为求职者，我希望同一基准简历可为多个职位生成多份优化简历，各关联对应职位卡，以便多岗位投递
40. 作为求职者，我希望优化过程中解析出的 JD 技能/关键词/要求被缓存，以便学习模块复用
41. 作为求职者，我希望可删除简历；删除基准简历不影响已生成的优化简历（独立副本），以便清理管理

### 学习模块

42. 作为求职者，我希望系统自动生成学习清单：JD 硬性要求 > JD 提及技能 > 简历缺口 > 项目技术栈（从未优化过简历时缺口部分留空，仅含 JD 与项目来源），以便知道该学什么
43. 作为求职者，我希望学习清单可人工增删、改优先级、标注来源，以便按自己节奏安排
44. 作为求职者，我希望点击学习条目即启动 teach 教学会话（聊天式界面，流式输出），以便高效学习
45. 作为求职者，我希望教学会话跨次续接（记住上次学到哪），以便长期学习不丢进度
46. 作为求职者，我希望学习条目三态（待学/学习中/已掌握）可手动切换，以便追踪进度
47. 作为求职者，我希望面试复盘产生的薄弱主题自动加入学习清单（来源标记"面试"），以便及时补短板

### 面试模块

48. 作为求职者，我希望针对某职位卡启动模拟面试（注入 JD 分析、我的优化简历、已掌握清单），以便检验准备程度
49. 作为求职者，我希望面试前选择风格：真实（默认，不中途点评）/ 教学（简短反馈）/ 压力，以便按需练习
50. 作为求职者，我希望按住说话进行语音回答（松开识别发送），本地离线识别，以便模拟真实面试
51. 作为求职者，我希望面试官按结构化流程推进：开场自我介绍 → 技术面（JD 硬性要求/简历项目深挖/已学清单检验）→ 反问环节 → 收尾，以便接近真实面试节奏
52. 作为求职者，我希望答得好时被深挖追问、答不出时被降级换题，以便练习有弹性
53. 作为求职者，我希望面试中可打断面试官、可补充说明，以便对话自然
54. 作为求职者，我希望面试结束时生成结构化复盘：总分 + 4 维度分（技术深度/表达逻辑/应变/匹配度）+ 亮点 + 薄弱点（含参考回答）+ 下一步建议，以便针对性改进
55. 作为求职者，我希望复盘中的薄弱主题可一键加入学习清单，以便立刻补短板
56. 作为求职者，我希望历史面试记录（对话 + 复盘）可回看，以便对比进步

（折叠自 wayfinder tickets #2-#12 与 ADR-0001~0007；不写文件路径与代码，详见各 ADR 与 ticket resolution）

- **技术栈**：Electron + Node/TS（≥22.19，ESM）+ Vue 3 + Vite + better-sqlite3 + pi SDK（ADR-0001/0002）。认证走 `ModelRuntime.create` 应用自有目录，不依赖用户全局配置
- **架构**：主进程合一承载全部服务；渲染进程经 contextBridge 类型化 IPC 通信；流式输出用事件推送。pi SDK 若遇内置 Node 不满足 ≥22.19，仅 agent 服务拆 utilityProcess（ADR-0001）。**服务层细化见 docs/architecture.md**：十服务接口（Settings/Position/Resume/ScoreEngine/Optimize/Topic/Interview/Crawl/AgentService/Asr，构造注入 db / agentProvider / fetcher）；类型化 IPC 协议（channel 如 positions:list、事件 agent:delta）；db migrations（PRAGMA user_version + 有序 SQL 数组）；渲染层 vue-router hash 路由 + composables；API key 存应用自有 auth.json（不落 SQLite）
- **数据模型**：6 张表——positions（职位卡）、applications（投递记录）、topics（学习条目，source 含 interview 枚举）、interviews（面试记录，transcript+review JSON）、crawl_runs（采集留痕）、settings（非敏感设置）；简历本体为 JSON（单一 schema 覆盖基准/优化稿，派生记 meta.baseResumeId/targetJobId，ADR-0003/0005）。去重：source_url 部分唯一索引优先 + dedupe_key（company|title|recruit_season）兜底；投递状态机 planned→applied→interviewing→offer/rejected/withdrawn。删除语义：职位/简历可删；删除基准简历不影响已存派生稿（副本独立）
- **匹配度模型**：规则层 5 维度加权（关键词覆盖 25/技能 25/项目 20/经历 15/学历 15，输出命中依据清单）+ LLM 定性分析；优化边界 optimizationMode 可配置（strict 默认/balanced）（ADR-0004）
- **agent 会话策略**：简历优化每次任务新建 inMemory session，会话内三轮（JD 解析→缺口评估→生成优化稿+改动说明）；面试一次一个长驻 session（steer 打断/followUp 排队，tools 收紧）；学习 cwd=教学工作区 + continueRecent 续接 + /skill:teach 显式触发（ADR-0002）
- **ASR**：sherpa-onnx-node（Windows x64 预编译）+ 流式中文模型 + Silero VAD 切句（静音≥1s）；PTT 按键说话触发（ADR-0007）
- **爬虫**：隐藏 BrowserWindow + executeJavaScript 提 DOM（零额外依赖）；牛客列表+翻页+详情页、猎聘 SSR 列表（无 end_date 置空）；手动触发 + 预览确认 + upsert 不自动关闭；节流 ≥2s、重试 2 次退避、上限 100 条（ADR-0006）
- **JD 分析缓存**：positions.jd_analysis（JSON 列：skills/keywords/requirements/hardRequirements/parsedAt），优化流程产出、学习模块复用，JD 更新时失效重算
- **简历渲染/导出**：A4 样式渲染 + Electron printToPDF；上传解析 docx→mammoth、PDF→pdfjs-dist，解析结果带置信度草稿，人工确认后入库
- **设置与认证**：设置模块（侧边栏第五入口）配置模型提供商/模型/API key（`ModelRuntime` 应用自有目录，auth.json，不落 SQLite）；首次启动引导配置 + 「测试连接」；**分层降级**：未配置/断网时手动功能（职位/简历/采集）照常，agent 功能（优化/学习/面试）提示配置，规则打分器独立可用
- **导航**：侧边栏常驻四模块 + 设置入口（UI 视觉细化另见 DESIGN.md，待 OpenDesign 细化后回填）

## 验收标准（MVP 完成定义）

- [ ] 四个模块均可从侧边栏进入并使用；设置页可配置模型并通过「测试连接」
- [ ] **闭环主线走通**：录入/采集一个职位卡 → 为其生成优化简历（看到匹配度 5 维度分与依据）→ 生成学习清单并完成一次 teach 会话（标记已掌握）→ 完成一次语音模拟面试（PTT 输入）→ 复盘产生并回填学习清单
- [ ] 分层降级正确：未配置模型时手动功能照常、agent 功能提示配置；规则打分仍可用
- [ ] 数据持久化：重启应用后职位/简历/清单/面试记录完好
- [ ] 采集留痕与去重正确：重复采集同一职位更新而非新建
- [ ] 服务层自动化测试全部通过（vitest，唯一 seam = services 层）

## Testing Decisions

- **好测试的定义**：只测服务接口的外部行为（输入 → 输出/副作用），不测实现细节；断言行为语义而非内部调用
- **唯一测试 seam：services 层**（已确认）。各服务构造时注入依赖：db 注入内存 SQLite（:memory:）；agent 服务注入 fake session provider（不触真实模型）；爬虫解析器与抓取分离——解析/映射/upsert 纯函数化可测，真实 BrowserWindow 抓取不做自动化测试（手动冒烟）
- **被测模块**：
  - 职位服务：去重（URL 优先/语义键兜底）、投递状态机、采集预览统计（新增/更新/缺字段）、upsert 刷新、删除语义
  - 简历服务：schema 校验、派生关系（baseResumeId/targetJobId）、解析草稿确认流程、基准删除不影响派生稿
  - 优化服务：规则打分器（5 维度纯函数，含边界：空简历/JD 无关键词/全命中）、prompt 组装、改动说明的结构校验
  - 学习服务：清单生成（优先级映射、去重、来源标记、无缺口降级）、状态流转
  - 面试服务：复盘 JSON 解析与 suggestLearn 联动、transcript 落库
  - 爬虫服务：牛客/猎聘字段映射（含猎聘无截止时间）、缺字段标记
- **测试框架**：vitest；本仓库无既有测试，这批是首批（prior art 无——测试即先例，后续沿用同模式）

## Out of Scope

- 自动投递（机器人代投简历）、社招信息、多用户/云同步、Android/移动端、全源爬虫铺开
- 二期/遗留（不入本 spec）：TTS（面试官语音输出）、定时采集、OCR（扫描件简历）、Computer Use 通道（见 ticket #11）、优化边界 balanced 模式细化、双栏 PDF 列合并、UI 高保真细化（DESIGN.md 待 OpenDesign）
