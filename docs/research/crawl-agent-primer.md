# 采集技术形态科普：CDP、Playwright 与 Agent 通道落地

> 写给产品 owner 本人（技术能看懂但不深）。背景：BOSS 采集优化已定"确定性抓取为主 + Agent 通道处理登录/异常"（并存模式），本文解释 Agent 通道的三个候选技术形态，帮你做最后一个技术决策。

## 0. 一句话总结（先看这个）

**你的应用已经内置了浏览器内核（Chromium），不需要再下载任何新浏览器。剩下要选的是"用什么遥控器去操作它"——手写遥控命令（内置 CDP），还是用封装好的遥控库（Playwright）。**

就像开车：你的车（Chromium）已经在了，A 方案是手动挡自己换挡，B 方案是自动挡（库帮你换挡），C 方案是再买一辆车（下载独立浏览器）——没必要。

## 1. 三个基础概念

### 1.1 BrowserWindow（回顾）

Electron 应用的界面窗口，本质是**嵌入式 Chromium**（Chrome 的开源内核）。采集功能现在开一个**隐藏的 BrowserWindow** 加载目标网站，用 `executeJavaScript` 取页面 DOM，用完销毁。

它已经证明能爬 BOSS（真实浏览器指纹，实测通过），短板是**交互不灵活**——复杂交互（登录扫码、异常重试、翻页）要人预先写死脚本。

### 1.2 CDP（Chrome DevTools Protocol）

- **是什么**：Chromium 内置的"遥控协议"。你按 F12 打开的开发者工具，本质上就是一个 CDP 客户端。
- **类比**：CDP 是给浏览器开的**驾驶接口**——导航、点击、输入文字、截图、读 DOM、监听网络请求，全部有标准命令。
- **关键事实**：**每个 Chromium 天生支持 CDP**，包括 Electron 里的那个。Electron 提供两种接入方式：
  1. `webContents.debugger`（官方 API，代码里直接挂载，零依赖）；
  2. `--remote-debugging-port` 调试端口（开一个本地端口，外部程序连进来）。
- **为什么重要**：`executeJavaScript` 只是 CDP 能力的子集。CDP 能做它做不到的事：**真实鼠标事件**（hover、拖拽，触发页面行为）、网络请求拦截、页面截图、性能数据。而且——市面上所有浏览器自动化工具（Playwright、Puppeteer、Kimi WebBridge）**本质都是 CDP 的封装**。

### 1.3 Playwright

- **是什么**：微软开源的浏览器自动化库（Node/Python 等），在 CDP 之上加了一层"高级封装"：你写 `page.click('#搜索框')` 这种**语义代码**，它内部翻译成 CDP 命令并处理等待、重试、元素定位。
- **类比**：CDP 是裸的驾驶盘，Playwright 是带定速巡航和自动泊车的驾驶系统。
- **两种使用姿势**：
  - **自带浏览器**：下载一个独立 Chromium（约 150MB），自己开自己管——与应用平行的"另一辆车"。
  - **连接现有浏览器**：`connectOverCDP()` 连到一个**已经在跑的** Chromium——**包括 Electron 里的那个**。不下载任何东西，复用现有内核。

## 2. 三个候选形态对比（这是你要做的决策）

| | A. Electron 内置 CDP | B. playwright-core 连 Electron CDP | C. playwright 独立浏览器 |
|---|---|---|---|
| **是什么** | 应用代码直接挂载自己隐藏窗口的 CDP 接口，发命令（点击/导航/截图） | 加 playwright-core 包（纯 JS、几 MB、**不下载浏览器**），连自己应用的调试端口 | 下载独立 Chromium（~150MB），平行跑 |
| **登录态** | 天然同进程，persist session 持久化 | 同 A（连的是同一个 Chromium） | 独立浏览器，**登录态与应用分开**，要重新登录 |
| **依赖** | **零新依赖**（符合 ADR-0006 原则） | 新依赖（打破零依赖原则，需写新 ADR） | 依赖 + 150MB 下载，最重 |
| **优点** | 最小改动；窗口管理已有 | API 成熟（等待/定位/事件/重试开箱即用）；开发快；社区生态大；将来换浏览器无痛 | 与主应用完全隔离；Playwright 全功能 |
| **缺点** | 底层 API：等待元素、重试、事件都要自己写，代码量大；文档少 | 调试端口暴露有安全面（需只绑 127.0.0.1 + 随机端口 + 用完即关） | 最重；维护两条浏览器；登录态分离 |
| **类比** | 手动挡 | 自动挡 | 再买一辆车 |

## 3. Agent 通道的完整链路（形态选好后长什么样）

```
用户点击"采集"
   │
   ├─ 常规路径：确定性抓取（现有解析器 + 隐藏窗口）——免费、快、已实测
   │
   └─ 需要登录 / 异常 / 复杂交互时 → Agent 通道：
        ① 隐藏窗口（登录态 persist session）导航到目标页
        ② 取页面快照（DOM 文本，必要时截图）
        ③ 现有 agent 层（pi SDK，你已配置好的模型）看快照，输出动作：
           "点击 id=xxx 的按钮" / "在搜索框输入 xxx" / "滚动"
        ④ 通过 CDP（形态 A 或 B）执行动作
        ⑤ 回到 ② 循环，直到任务完成或交给用户
```

要点：
- **登录态是薪资的钥匙，与形态无关**——persist session（cookie 存本地磁盘）扫码登录一次，以后复用。A、B 都支持，C 要单独搞。
- **成本可控**：因为"并存"，LLM 只在登录/异常时介入，常规采集不花模型钱。
- **测试**：Agent 通道的真实浏览器行为不做自动化测试（与现有采集一致，spec 已有此决定），手动冒烟。

## 4. 我的推荐

**B（playwright-core 连 Electron CDP）工程性价比最高**，理由：

1. 它驱动的是**同一个 Chromium**（你的隐藏窗口），登录态、指纹、风控表现与现有机制完全一致——不用 C 的原因；
2. 相比 A，等待/定位/重试这些 Agent 循环里最烦的活 Playwright 全包了，开发量省一半以上，出 bug 的概率也低（这是社区大规模验证过的 API）；
3. 代价是打破 ADR-0006 的"零额外依赖"——但这不是坏事，是**该写新 ADR 的时刻**（决策记录：为什么从零依赖转向接受一个成熟依赖），正好实践仓库的 ADR 纪律；
4. 安全面可控：调试端口只绑 127.0.0.1、随机端口、任务结束即关。

**A 完全够用，如果你更在意"最小改动 + 零依赖"**：代价是 Agent 循环的等待/重试逻辑手搓，代码量明显更大。

**无论 A/B**：登录态 persist session 都要做（这是薪资的钥匙）。

---

## 5. 决策帮助（最后一段）

- 你的应用已经内置 Chromium → **排除 C**（不需要再买一辆车）。
- A 和 B 驱动的是**同一个浏览器**，区别只是"自己手写遥控命令"还是"用封装好的遥控库"。
- 选 A = 省依赖、费开发；选 B = 加依赖、省开发。
- 这是一个"真实取舍"，定了之后写成 ADR-0008 记录。
